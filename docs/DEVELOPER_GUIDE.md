# Implementing features in Flowline

This guide applies to developers and AI agents. Start with [AGENTS.md](../AGENTS.md), the feature request, and the nearest existing implementation. Read the relevant installed guide under `node_modules/next/dist/docs/` before changing Next.js code. Preserve working behavior and stay within the authorized scope.

## Feature workflow

Track every task on GitHub first: issue, milestone, labels and the project board, as described in [GITHUB_WORKFLOW.md](GITHUB_WORKFLOW.md).

1. Identify the route, server API, permissions, persistence and UI states affected. Inspect existing patterns before adding abstractions.
2. Define real loading, empty, error and success behavior. A successful HTTP request must be checked before displaying success. Unbuilt actions use a disabled control with a translated reason.
3. Add Arabic and English copy together, including field labels, validation, tooltips, accessible names and metadata.
4. Use shared controls and semantic design tokens. Provide keyboard operation, visible focus and narrow-screen layouts.
5. Enforce server validation, authorization and the existing mutation/CSRF guards. Client validation is only feedback.
6. Add meaningful tests for changed behavior, run the required gates and record exact evidence and remaining external checks.
7. Update every Markdown doc the change affects in the same PR (AGENTS.md "Docs (mandatory)"); the `Docs` workflow fails a non-draft code/config PR with no `.md` change outside `artifacts/` unless it carries the `docs-not-needed` label and an unindented plain-text PR body line `Docs not needed because: <reason>` with a real reason on that same line (not blank and not the literal `<reason>` placeholder). Body edits rerun the check. Verify commands, paths, configuration and status against the repository; mark external results unverified.

The docs check (`scripts/ci/docs-check.mjs`) covers `src/`, `worker/`, `scripts/`, `e2e/`, `tests/`, `drizzle/`, `deploy/`, `.github/` and these root files: `package.json`, `pnpm-lock.yaml`, `Dockerfile*`, `docker-compose*.yml`, `next.config.*`, `tsconfig*.json`, `drizzle.config.*`, `vitest.config.*` (including `vitest.config.mts`), `playwright.config.*`, and `*.config.{ts,mjs,js,cjs}`. The workflow checks out the script without installing dependencies, reads paginated PR filenames as JSON (preserving spaces), and supplies the event PR body through `PR_BODY`. A label alone, an empty/whitespace-only reason, the unfilled template placeholder, or a different format does not waive the check. The placeholder is rejected when the reason is only `<reason>` (any case or inner spacing, optionally in backticks or quotes, with trailing punctuation), any other lone `<...>` token such as `<explain why>`, or the bare word `reason`; a reason that still contains the `<reason>` token anywhere is also rejected (a real explanation never includes it), while other sentences, even ones starting with the word "reason", are accepted, and each body line is judged on its own. GitHub's PR files API returns at most 3000 files, so a list of 3000 entries or more may have dropped code files: the check then assumes code changed (a visible Markdown change outside `artifacts/` or a valid waiver is still required) and says so in the step summary and a `::warning::`. See the PR template for the exact format. Both rules are fixture-tested in `tests/unit/docs-check-script.test.ts`.

Toolchain: Node.js 24.x (`engines`; CI and the release image use Node 24 LTS), pnpm 10.32.1, Next.js 16.3.6 and React 19.3.0 (`package.json`). Use `pnpm.cmd` on Windows if the PowerShell launcher fails. Security advisories for transitive dependencies (such as Dependabot alert #3 for `source-map-js`, GHSA-68fv-2mgg-jv7q) are overridden in `pnpm-workspace.yaml` under `overrides` and validated via `tests/unit/dependency-advisories.test.ts` (see [DEPENDENCIES.md](security/DEPENDENCIES.md)).

## Localization

The complete canonical catalogues are `src/i18n/messages/ar.json` and `src/i18n/messages/en.json`. Arabic defines the key shape; English must match. Preserve placeholders and plural categories. Use nested JSON objects rather than dotted literal keys. Use `useT()` from `@/i18n/client` in client components and `await getT()` from `@/i18n/server` in server components. Keys remain dotted paths in code, for example `t("account.email")`.

Use `t.plural()` for count messages and the translator's `number`, `date`, `relative`, `duration` and `percent` helpers for localized formatting. Both locales use digits 0–9 (`src/i18n/config.ts` / `format.ts`); Arabic remains RTL. Translate product catalogue content by stable ID. Never concatenate translated sentence fragments. Review wording in context rather than only checking key parity.

Arabic and light are the defaults. English and dark remain selectable. Use logical CSS (`ms`, `me`, `start`, `end`) and keep emails, URLs, code and credentials LTR. The owner copy editor at `/admin/copy` (`src/app/admin/copy/copy-editor.tsx`, props, step-up and write behaviour in its JSDoc) provides protected draft/preview/publish overrides; developer JSON remains the base catalogue.

## Components and design

Import shared primitives from `@/components/ui`. [FORMS.md](design-system/FORMS.md) describes schema forms and [CUSTOMIZE.md](design-system/CUSTOMIZE.md) describes the token pipeline. Change `fields.tsx` for shared input presentation and `button.tsx` for shared button presentation rather than copying their classes into pages.

The existing token pipeline starts at `src/design/tokens.ts`, generates CSS with `pnpm tokens`, and is consumed through `src/app/globals.css` and Tailwind v4 `@theme`. Do not introduce a second palette or hand-edit generated outputs. Use semantic utilities such as `bg-card`, `text-hi`, `border-line` and `bg-accent`.

Use meaningful existing Lucide icons; preserve textual accessible names. Motion must be at most 300 ms, honor reduced motion, and never lift cards on hover. Backgrounds are decorative and must not intercept clicks or obscure text. Section navigation uses query parameters, never URL fragments.

## Server, data and security

Use the relevant `src/server/access.ts` helper (`requireWorkspace`, `requireFlow`, `requireRun`, etc.) before accessing workspace resources. Authentication alone is insufficient: enforce the requested role/capability and preserve non-member 404 behavior. Follow existing route wrappers for mutation validation and CSRF; App Router does not automatically protect arbitrary route handlers.

Persist flows, versions, runs and steps in Postgres. Change `src/db/schema.ts` and run `pnpm db:generate` for schema changes; retain the generated migration and metadata. A data backfill must be safe to run twice; when it overwrites data, it keeps the old values in a backup table and ships a reverse script under `drizzle/reverse/` (outside the journal, run by hand with `psql -v ON_ERROR_STOP=1 --single-transaction -f`), tested in `tests/integration/` (example: `flow-version-run-backfill.test.ts`). Engine connection rules belong in shared `checkConnection`.

Backfill 0026 and its manual reverse hold a `SHARE ROW EXCLUSIVE` lock on `flow_version` through commit, with transaction-local lock/statement timeouts of 5/30 seconds. Writers wait while readers continue; run the focused migration integration spec on an isolated test database before deployment. A timeout aborts the transaction rather than leaving triggers disabled or clearing unbacked numbers.

Provider credentials use uncontrolled `SecretInput` plus `takeSecret`; never store them in controlled form state, drafts, URLs, query caches or evidence. Follow `docs/security/CREDENTIALS_DESIGN.md`. Account login/recovery forms have their existing dedicated handling; do not generalize that exception to provider secrets.

Use `parseBody`/`capBody` before parsing untrusted bodies. The shared reader has a 10-second total read deadline by default and byte caps; only the files and knowledge upload routes pass `UPLOAD_BODY_READ_TIMEOUT_MS` (90 seconds, the longest deadline `capBody` accepts, sized for 5 MiB at 512 kbit/s). deploy/beta Caddy applies the earlier socket deadline and route caps, with the same per-route values (`read_body 10s`, and `read_timeout 90s` on the upload block); change both sides together. Keep new route exceptions aligned with [REQUEST_BODY_LIMITS.md](security/REQUEST_BODY_LIMITS.md), which documents direct-Next.js and hosting limitations. Focused checks (one worker, no DB/browser):

```powershell
pnpm.cmd exec vitest run --project unit --configLoader runner tests/unit/http-capbody.test.ts tests/unit/http-body-deadline.test.ts tests/unit/upload-route-deadline.test.ts tests/unit/proxy-body-limits.test.ts tests/unit/public-body-budget.test.ts tests/unit/public-route-body-budget.test.ts tests/unit/knowledge-errors-i18n.test.ts tests/unit/platform-units.test.ts --maxWorkers 1 --no-file-parallelism
```

Unit tests exercise concurrent-transaction behaviour without Postgres through `runConcurrent(txA, txB, { timeoutMs })` in `tests/helpers/concurrentTx.ts`: a two-party barrier holds each transaction at its first lock until both have arrived, an error with `code === "40P01"` is reported as a deadlock, and a hung pair rejects after `timeoutMs` (the timer is cleared in `finally`, so no handle is left open). The fakes-only suite `tests/unit/concurrentTx.test.ts` covers the barrier, the deadlock mapping and the timeout in the `unit` project; integration suites never run it.

Preserve invitation-only signup when configured, verification requirements and test-only environment boundaries. The complete server-only `ZITADEL_ISSUER`, `ZITADEL_CLIENT_ID`, `ZITADEL_CLIENT_SECRET` tuple takes precedence over encrypted platform DB settings; all absent permits that legacy configuration, but a partial or malformed tuple disables ZITADEL without fallback. Restart web processes after environment changes; never expose the tuple to customers. Workspace SSO has its own configuration and callback path. Test-double success does not establish live tenant readiness. Billing remains sandbox-only.

Federated sign-in for enrolled users issues only a pending local-TOTP challenge. The shared Better Auth adapter rejects unassured sessions for both application access and the library's account APIs; retain disabled session-cookie caching and authoritative DB reads. MFA proof is tied to the current factor and has a fixed expiry even when the session refreshes. A transaction that locks the user, session and authority rows of these flows must follow the lock order in [FEDERATED_MFA.md](security/FEDERATED_MFA.md#lock-order) (use `lockUserThenSessions` from `src/server/federated-locks.ts`); `tests/unit/federated-lock-order.test.ts` pins it. Every audit insert takes a key-share lock on the `workspace` row, so a transaction that locks a `workspace` row and then waits for a member row must use `FOR NO KEY UPDATE`, never `FOR UPDATE` (`lockWorkspaceMembership` in `src/server/members.ts`; [Member changes](security/FEDERATED_MFA.md#lock-order); `tests/unit/member-lock-order.test.ts` pins it). Review any new transaction that takes row locks against the global order and checklist in [engineering/lock-order.md](engineering/lock-order.md). See [FEDERATED_MFA.md](security/FEDERATED_MFA.md) before adding session storage, sign-in methods or account-linking paths.

## Verification and handoff

Run focused local checks such as `pnpm lint`, `pnpm typecheck`, and `pnpm test`; stop the test stack with `pnpm stop:test` before integration tests. The helpers in `src/lib/format.ts` (`percent`, `pretty`, `initials`, `duration`, `timeAgo` and the money helper `toDecimalString`) are pinned by `tests/unit/lib-format.test.ts` (English and Arabic, no DB or browser): `pnpm exec vitest run --project unit tests/unit/lib-format.test.ts`. `toDecimalString(value, scale = 2)` converts a number or decimal string to an exact fixed-scale string by string/digit manipulation only, with no float arithmetic or rounding: it normalises Arabic-Indic digits (`٠-٩`) to `0-9`, rejects Persian digits and the Arabic decimal separator `٫`, and throws (rather than truncating or rounding) when the value needs more decimals than the scale, for scale 0 too. UI changes require browser coverage through CI. The GitHub Actions workflow `.github/workflows/gate.yml` runs the fast tier on PRs and pushes to main; the full tier (every Chromium spec, Firefox, WebKit) runs only from `workflow_dispatch` with `tier=full`. Run `pnpm gate` locally only when explicitly needed. Respect any feature flags required by the feature under test.

Natural-language e2e-army tests (`e2e-army/<issue>-<flow>.e2e.ts`, the blocking `e2e-army` status) are copied and run by the hub's verify job, which type-checks them against its own `e2e` and `@e2e-dev/web` packages. Both are devDependencies here (issue #85), but `tsconfig.json` still excludes `e2e-army/` from `pnpm typecheck` until follow-up #217 type-checks the folder. `pnpm lint` still covers the folder.

### Field-run and other synthetic sign-up harnesses

A harness that creates its own users through the public `/api/auth/sign-up/email` endpoint and reads the verification link from `/api/test/outbox` (the `signUpFieldUser` helper of the field-validation v2 harness, `scripts/field-validation/v2/signup.ts`, which lives on branch `claude/issue-6` and is not on `main` yet) needs the target server started with **both**:

- `FLOWLINE_ENV=test`: the test outbox and the other `/api/test/*` routes answer only in the test environment; elsewhere they are 404.
- `FLOWLINE_BETA_MODE=open`: with `invite_only`, a sign-up without an invitation, access code or `FLOWLINE_BETA_ADMINS` entry is refused (`src/server/beta.ts`), and so are a missing or invalid value, which default to `invite_only` and log a configuration error. `FLOWLINE_ENV=test` does not relax this by itself; only the isolated E2E stack's per-context `fl_test_beta_mode` cookie does.

Start the stack with both variables set (the isolated stack from `scripts/test-stack.cjs` and the `flowline_test_<suffix>` database rules in "CI gate" below still apply), for example `FLOWLINE_ENV=test FLOWLINE_BETA_MODE=open` in the server's process environment, never in a shared env file. The v2 harness README on that branch does not list `FLOWLINE_BETA_MODE=open` yet; add it there when the branch is merged.

### Git hooks and local CI

`pnpm install` runs `prepare: husky || true` (so a production-only install without dev dependencies, where the `husky` executable is absent, still succeeds, as in Husky's documentation), which installs the hooks in `.husky/` (husky sets `core.hooksPath=.husky/_`, a path that only exists in a checkout where `pnpm install` ran). They are deliberately fast; the full CI runs on the owner's Mac mini through the hub's `localci` job, which posts the GitHub commit statuses under the workflows' job names.

- `pre-commit` (staged files only, about 1-5 s; hard limit 60 s; on expiry the watchdog sends SIGINT first and waits up to 20 s so lint-staged can restore the unstaged edits it hid for partially staged files, and the timeout message says how to recover them from lint-staged's backup stash if it had to be killed): `lint-staged` runs `eslint --fix` on staged `*.{ts,tsx,js,jsx,mjs,cjs}` (config: `"lint-staged"` in `package.json`; the repo has no Prettier). Fixes are re-staged; remaining errors block the commit.
- `pre-push` (about 10-25 s; hard limit 290 s, the 5-minute rule): `tsc --noEmit`, `vitest related --run --project unit <files the push changes>` (the whole unit project when the base is unknown, the push deletes a code file, or `package.json`, the lockfile, `vitest.config.mts` or a tsconfig changes) and `node scripts/check-evidence-secrets.mjs`. No database, integration, contract, browser or build.

Both hooks work in linked worktrees: `pre-push` drops git's hook environment (`GIT_DIR`, `GIT_INDEX_FILE`, ...) before running tools, while `pre-commit` keeps it because lint-staged must use the active index. Neither prompts, and in a worktree without `node_modules` print a one-line skip note and exit 0 instead of installing anything. Bypass deliberately with `HUSKY=0` (any hook) or `SKIP_LOCAL_CI=1` (pre-push). A skipped or bypassed hook is not evidence; the `gate` and `docs` checks still decide merges.

### CI gate

Main's ruleset requires two checks: `gate` (the combiner job in `gate.yml`) and `docs` (`docs.yml`). Every non-draft PR event (`opened`, `synchronize`, `reopened`, `ready_for_review`), push to main and dispatch therefore reports a real `gate`. There is no `paths-ignore`; the first job, `changes`, classifies the change set with `scripts/ci/changed-scope.mjs` (unit-tested in `tests/unit/changed-scope.test.ts`). For a PR it reads the paginated PR files API (`pull-requests: read`, with renamed files counted under both paths); for a push it reads the compare API from the previous main commit, and runs the test jobs when that comparison is unavailable; a dispatch always runs them. A change is docs-only when every path is under `docs/` or `artifacts/`, or is a `*.md` file at any depth (case-sensitive); `design-reference/` always counts as code because unit tests read it. Anything else is code, including unknown root files, an empty list, a PR file list of 3000 files or more and a push comparison of 300 files or more. Those are GitHub's caps (the PR files API stops at 3000; the compare API returns at most 300 files, and only on its first page, because `--paginate` adds later pages of commits but not more files), so a list that long may be truncated; it counts as code and the script logs a `::warning::` with the counts. PR entries are counted across pages and compare entries by distinct filename, a rename is one entry, and later compare pages that carry commits only are accepted. When the change is docs-only, `checks`, `chromium`, `firefox` and `webkit` are skipped and `gate` passes with "docs-only change: test jobs skipped by design". A failed or cancelled `changes` job, or an unreadable PR file list, fails `gate`.

Fast tier jobs: `changes`, `checks` (a matrix of legs on separate runners: static·unit·contract, plus integration shards 1/3, 2/3 and 3/3, each with its own PostgreSQL) and `chromium` (`@critical`/`@cross-browser` specs). The full tier adds `firefox`, `webkit` and every Chromium spec. The `gate` job runs even after a failure and passes only when `changes` succeeded and every test job succeeded (docs-only: every test job skipped; firefox and webkit may also be skipped on the fast tier); its summary lists every job. On a draft PR every job, `gate` included, is skipped so no runner is allocated; a draft cannot merge, and leaving draft starts a real run on the same commit. Open the PR's **Checks** tab and select a job (or **Gate**) to see its step summary; each test job, and each `checks` leg, uploads its own `flowline-gate-<leg>-<run id>-<attempt>` artifact (`checks-static`, `checks-integration-1of3` to `3of3`, `chromium`, `firefox`, `webkit`) with its logs, `summary.json`, browser text reports, the Playwright JSON reports and failure context (14 days), and, only when a browser test failed, a `-traces` artifact with the failing tests' `trace.zip` files (7 days). See [Playwright traces in CI](#playwright-traces-in-ci). The static leg's report is written by `pnpm gate`; every integration shard writes its own through `scripts/ci/integration-shard.mjs` (it tees the vitest output into the job log and `integration-<k>of<N>.log`, and leaves a failed `summary.json` before vitest starts so a killed or timed-out shard is never a missing report), tested in `tests/unit/ci-integration-shard.test.ts`. The `gate-report` action reads only the `summary.json` of its own leg and rejects one that names a different shard, so a static report is never read as a shard result or the reverse.

Gate has no `labeled` trigger and the `full-gate` label no longer does anything. GitHub treats a skipped job as a passing required check, so a label added after a real failure would otherwise start a no-op run whose skipped `gate` could mask it; with no such trigger, the only skipped `gate` is a draft's, which cannot merge (`docs.yml` is the exception by design: it reruns on `labeled`, `unlabeled` and `edited` because its waiver depends on them, and it never skips except for drafts). To run the full tier, once on the final candidate just before merging, use **Actions → Gate → Run workflow**, choose the branch, set **tier** to `full`, and start the run, or run `gh workflow run gate.yml --ref <branch> -f tier=full`. The run reports the same job names on the branch head, and the owner verifies its pass before merging. The `fast` dispatch option remains for a targeted rerun.

Actions are pinned by full commit SHA with a `# vX.Y.Z` comment (checkout v7.0.1, setup-node v7.0.0, upload-artifact v7.0.1, pnpm/action-setup v6.1.0, cache v6.1.0; all Node 24) and every job runs on `ubuntu-24.04`, so a moving tag or `ubuntu-latest` cannot change CI silently. Upgrade by resolving the latest release tag to its commit (`gh api repos/<owner>/<repo>/releases/latest --jq .tag_name`, then `gh api repos/<owner>/<repo>/commits/<tag> --jq .sha`), reading its release notes for input changes, and keeping the comment current; `tests/unit/ci-workflows.test.ts` fails on an unpinned action or a floating runner.

The blocking E2E gate for AI pull requests is the hub's `e2e-army` commit status (tester-army/e2e, natural-language steps): its verify job starts the app from the branch and runs its FlowLine suite together with up to 8 top-level `e2e-army/*.e2e.ts` files of the branch (the first 8 by name; `features/` is not copied). Every PR, backend-only ones included, adds or updates an `e2e-army/*.e2e.ts` test tagged `feat:<id>` for each feature its changed files touch (mapped by the `paths` globs of the hub's feature map; a backend-only change runs the feature's api-level shard; waiver: `E2E: not needed — <reason>` in the PR description); files no feature claims run the smoke shard and are reported as "feature map gap" until the feature map claims them. A PR that changes a user flow adds or updates `e2e-army/<issue>-<flow>.e2e.ts` in its first commit; the title carries `@issue-<N>` and the acceptance criterion, each `agent.act` has one goal and is checked with `agent.assert` or an exact `expect`, and the file imports only `e2e`, `@e2e-dev/web` and node built-ins. Signed-in tests use `{ session: "fl-user" }`, which the hub suite's setup provides, and `e2e-army/features/_setup.e2e.ts` does the same locally (never declare a second `fl-user` setup at the top level: the hub runs both files together and one session name allows one setup). Tests that need the owner's workspace open `/app`, which continues in it. The per-feature suite (a port of the hub's, one or more `[<feature>.<n>]` tests per entry of the feature map, tagged `feat:`/`shard:`/`lvl:`) lives in `e2e-army/features/` (the hub keeps its own copy and copies only the top-level files); run one shard with `pnpm e2e:army --shard-id core-api` (smoke, core-api, flows-api, runs, triggers, schedule, ai-api, platform-api, ui-auth, ui-auth2, ui-flows, ui-builder, ui-settings, ui-ai, ui-admin, ui-misc). Run the quick default with `pnpm e2e:army` (`scripts/e2e-army.mjs`, config `e2e.config.ts`): it starts the test stack on :3100 (or reuses a running `pnpm dev:test`; `E2E_ARMY_URL` points it at another app; the browser and the API helpers both take that origin from `appUrl()` in `e2e-army/lib.ts`, default `http://localhost:3100`, so cookies set by one reach the other), uses `agy` (Gemini Flash, the owner's login) when it is on `PATH` or `E2E_ARMY_CLI=agy|claude`, skips the agent tests without a model, keeps telemetry off; budget 5 min per shard, enforced by `scripts/e2e-army.mjs`; not yet timed in CI. Output and the replay cache are in `.e2e/` (git-ignored); the cache replays on a throwaway database, while on a persistent local one the UI tests' workspaces get a `-2`, `-3` … slug on each repeat run (no API deletes a workspace) and their steps are re-recorded. The resend-verification UI test checks the real 60 s cooldown (`requestToken`): inside it the page answers neutrally and no second mail is sent. Chromium comes from `pnpm exec playwright install chromium` (the same Playwright 1.63 build). No GitHub Actions job runs the suite yet; the Playwright specs stay as plain tests.

Tests default to port 3100 and `flowline_test`; isolated stacks use the ports and `flowline_test_<suffix>` databases from `scripts/test-stack.cjs`, never the development database. `pnpm test:e2e` selects all three configured browsers; use `--project=chromium --project=firefox` for only those two. English suites use `EN_STATE`; Arabic/RTL needs explicit coverage. No deleted assertions, hidden failures, retries presented as clean passes, or skipped acceptance checks.

For browser timeouts, distinguish the whole-test deadline from time spent on the final action: the 60 s Playwright timeout covers the whole test, so a click that fails may have started late because earlier actions used up the budget. A failed browser job uploads what tells the two apart (the trace and the JSON report, see [Playwright traces in CI](#playwright-traces-in-ci)); a trace path printed in a text report is only a path on the runner, so download the artifact instead of relying on the report. See [the PR #14 WebKit diagnosis](implementation/WEBKIT_14_DIAGNOSIS.md) for the exact three-stack comparison and isolated-journey commands; these require a dedicated test environment, not a shared laptop session with heavy checks prohibited.

Store evidence under `artifacts/phase-N/` with tested SHA and, for uncommitted work, a source fingerprint. Report exact checks and external blockers. No secrets or customer data in artifacts. Production deployment, live payments and release-scope changes require explicit owner approval.

Lock-order regression tests (deadlock checks against real Postgres) use `runConcurrentPg(txA, txB, { timeoutMs })` from `tests/helpers/concurrentPgTx.ts`, built on the DB-free `runConcurrent` core: it opens one connection per transaction, wraps each callback in `BEGIN`/`COMMIT` (`ROLLBACK` on error), passes it `{ client, arrive }` so both can hold their first lock before either takes its second, and rejects with `deadlock detected (40P01): …` or `runConcurrent timed out after <n>ms`. On any failure it ends both backends with `pg_terminate_backend` from a third connection, so a hung lock wait never outlives the test. Usage example in the file header; its tests are `tests/integration/concurrent-tx.test.ts` (advisory locks) and `tests/integration/concurrent-tx-pg.test.ts` (row locks on two scratch tables, unique per run and dropped in `afterAll`: an opposite-order pair is reported as `40P01`, a same-order pair finishes, an error thrown before `arrive()` rejects at once while the other side waits at the barrier, and no row lock or idle-in-transaction backend is left behind). They need the test database, so they run in the integration project, not `pnpm test`. The DB-free `tests/unit/concurrentPgTx.test.ts` (issue #192, the review findings of PR #125) replaces `pg` with a scripted fake and pins three cleanup rules in the `unit` project: a client whose `pg_backend_pid()` query fails after `connect()` is ended along with the other one, `timeoutMs` also bounds opening the connections (a connection that finishes later is ended), and a `40P01` from one callback is reported at once without waiting for the other, after both backends are terminated.

Local evidence helpers that start Vitest against a disposable database (`artifacts/phase-4/paid-pilot-round1/upload-admission/run-focused.mjs`, `.../federated-mfa/run-focused.mjs`, `.../paid-pilot-round1/run-auth-focused.mjs` and `artifacts/phase-4/security-auth/run-focused.mjs`) must not pass `process.env` to the child, because an ambient `FLOWLINE_*`, provider key or `NODE_OPTIONS` would silently change what a run proves. They call `buildFocusedTestEnv` from `scripts/focused-run-env.mjs`: the child gets only OS/runtime names the parent has (`PATH`, temp/home directories, the Windows system variables, `NODE_OPTIONS` when set) plus the synthetic values the helper constructs, and the call refuses anything but `FLOWLINE_ENV=test` and a `flowline_test` or `flowline_test_<suffix>` database. The variable names (never values) go into the result JSON (`childEnv`) or stderr, and `--dry-run` prints them without git, Docker or a database (`run-auth-focused.mjs` and `security-auth/run-focused.mjs` read the target from `DATABASE_URL`, so it must be set even for `--dry-run`). A new helper reuses the module and joins the list in `tests/unit/focused-run-env.test.ts`. CI's unit job runs that test (the helpers' `--dry-run` included) but never a helper's real database run. Other scripts that spread `process.env` (`check-drizzle-prune.mjs`, gate, release, Company Builder and the frozen `artifacts/beta-execution` and `artifacts/design-v2` helpers) are not database-backed focused runs and are unchanged.

### Playwright traces in CI

Added for [issue #35](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/35) so an intermittent browser failure leaves per-action timings behind. The upload logic is `.github/actions/gate-report/action.yml`; it has been checked by `tests/unit/ci-workflows.test.ts` and a local run of its summary step with fake data, and has not yet uploaded a real trace on GitHub (that happens on the first failing browser test after it merges).

**What is recorded.** `playwright.config.ts` sets `use.trace: "retain-on-failure"` and `retries: 0`. Each test is traced while it runs and the trace is kept only if the test fails: one `trace.zip` per failing test, merging all of its browser and API contexts, so a green run has no trace. The gate's browser runners (`scripts/gate-browser-native.mjs`, `e2e/tools/browser-docker.sh`) pass `--reporter=line,json`, which replaces the config's reporters, so the JSON report of each shard is `test-results/<browser>-<shard>-results.json` and the traces sit in the shard's output folder, `test-results/<browser>-<shard>/<test folder>/trace.zip`. Neither retries nor longer timeouts are added to get a trace; a flaky test is still a failure.

**Where to find it.** Open the failed run, then Artifacts. The job's step summary (Checks tab) lists the failed browser tests and names both artifacts.

| Artifact | Kept | Contents |
| --- | --- | --- |
| `flowline-gate-<job>-<run id>-<attempt>` | 14 days | gate logs and `summary.json`, `test-results/<browser>-<shard>-report.txt`, `<browser>-<shard>-results.json` (uploaded on every run, passes too: per-test start time, duration and errors), `error-context.md` and failure screenshots |
| `flowline-gate-<job>-<run id>-<attempt>-traces` | 7 days | the `trace.zip` of each failed browser test; not created when no test failed |

Download and open a trace on your own machine: `gh run download <run id> -R AbdelrhmanAh7/FlowLine_Web -n flowline-gate-webkit-<run id>-<attempt>-traces`, then `pnpm exec playwright show-trace <folder>/trace.zip`. Do not open it in an online viewer. To separate the whole-test deadline from a stalled action, compare the test's start with the failing action's start and duration in the trace (the timeline shows every action, `expect` and `test.step`); the same test's `startTime` and `duration` are in the JSON report. A failing action that started with most of the 60 s still unspent points to an actionability or scheduling stall, and one that started near the end means earlier actions used the budget (the ranked hypotheses are in [the WebKit diagnosis](implementation/WEBKIT_14_DIAGNOSIS.md)). Copy what you need, as sanitized timings, under `artifacts/phase-N/` before the artifact expires.

**Why a trace cannot leak a secret.** A trace records the actions with the text typed, DOM snapshots, screenshots, the page's network log with request and response headers and bodies (cookies and `Set-Cookie` included), console messages, the test source and test attachments. It does not record environment variables, server logs, `.env.test` or the runner's `GITHUB_TOKEN`. This repository is public, so signed-in GitHub users can download its artifacts; what keeps traces safe is:

1. Everything a trace can contain comes from the browser talking to the disposable CI stack on `localhost` and the fake providers on `127.0.0.1`: the fixed test password (`PASSWORD` in `e2e/helpers.ts`), session cookies and verification links that only work against that run's database, and fake provider keys (`sk-fake-…`). Server-side secrets are never sent to the browser, so they appear only through effects such as signed cookies.
2. `setup-gate` generates the database password, auth secret and encryption keys with `openssl rand` on every run, masks them, and the database is destroyed with the runner; the provider credentials in `.github/ci/env.test.template` are fakes.
3. The gate workflow and its actions use no `secrets.*`, and no browser job reads `github.token` (only `changes` does); the workflow's default permission is `contents: read`.
4. `e2e/admin-panel.spec.ts` and `e2e/keyboard-surfaces.spec.ts` reveal write-only credentials in the UI and so call `test.use({ trace: "off", screenshot: "off", video: "off" })`, which keeps their canary values out of evidence.
5. Traces are kept 7 days and are never committed: `artifacts/**/test-results*/` is git-ignored, and `scripts/check-evidence-secrets.mjs` skips zip files, so it cannot vouch for one.

`tests/unit/ci-workflows.test.ts` pins points 3 and 4 and the upload globs. Rules that keep it true: never put a real credential in a spec or a CI environment value; a new spec that reveals a write-only secret must switch tracing off like the two above; keep raw trace files out of the repository and commit only sanitized findings.

## Worktrees

Agent lanes live under `.claude/worktrees/<name>` (git-ignored), with `node_modules` linked to the main install. Run `pnpm wt` from any checkout; the branch defaults to the lane name, and `add` always creates a new branch.

```bash
pnpm wt add my-lane                               # new branch my-lane from origin/main; prints the path
pnpm wt add branch-lane --branch feat/branch-lane  # slashed branch, bare lane name
pnpm wt add base-lane --base origin/dev           # choose the start point
pnpm wt list                                        # <path> | <branch> | dirty=<n> | pushed=<true|false>
pnpm wt remove my-lane                              # alias of rm; refuses dirty or unpushed work
pnpm wt prune                                       # clear stale registrations; remove clean, pushed lanes
```

Safety rules:

- Lane names must match this pattern; `add` rejects anything else before git runs:

  ```
  ^[A-Za-z0-9][A-Za-z0-9._-]*$
  ```

  Use `--branch feat/x` for a slashed branch name.
- The `node_modules` link `add` creates is the helper's own and is not counted as a change, so a fresh lane is `dirty=0` and can be removed straight away; a `node_modules` that is not that link counts as work. `rm`/`remove` refuse dirty or unpushed work with exit 1 and a clear message, e.g. `refusing to remove <path>: 1 uncommitted change(s); commit or discard them first`. Removal never forces and never deletes the branch.
- Removal requires a registered worktree and refuses the main checkout and locked lanes. Bare names select only managed lanes; an external worktree needs an explicit path (absolute, or containing `/` or `\`), and relative paths resolve from the current directory. Path comparisons normalize separators and ignore case only on Windows.
- `list`/`prune` skip missing directories and locked lanes, report per-lane errors, continue with later lanes, and exit nonzero on an error. `prune` keeps dirty or unpushed lanes; do not run it while agents are starting lanes.


### Pilot CSV input persistence and admin 404s (2026-10-15)

Run input uses PostgreSQL `json` (migration 0027), preserving a caller's first-row key order when the
worker builds CSV. The CSV serializer uses that order; do not sort the keys or change run input back
to `jsonb`. Existing rows already reordered by `jsonb` cannot recover their original key order.
Flow graphs and other JSONB columns are unchanged. CSV rows produced inside the engine keep their
expression-defined order. Regression coverage: `tests/integration/runs.test.ts` and
`e2e-army/features/runs.e2e.ts` (`feat:fl-csv-data-node`).

Admin page metadata is subject to the same platform-admin authorization boundary as page content.
Denied `/admin`, `/admin/copy`, and unknown admin paths return 404 without authenticator/setup/copy-editor
text, including in embedded metadata. Next.js may use its `__next_error__` envelope for `notFound()`;
the HTTP status and absence of restricted content determine the contract. Auth, session MFA and TOTP
requirements remain enforced. Saved flow snapshots intentionally have `version: null`; publication
numbers and draft revisions are distinct (CTO decision #204, phase-4 ledger).
