## What the local integration does

The operator configures the platform ZITADEL Web application with the complete server-only environment tuple `ZITADEL_ISSUER`, `ZITADEL_CLIENT_ID` and `ZITADEL_CLIENT_SECRET`. The exact HTTPS issuer origin and client credentials are read server-side; changing them requires restarting web processes. A partial or invalid tuple disables ZITADEL and never falls back to stored credentials. When all three variables are absent, the older encrypted platform DB setting and credential remain a backward-compatible configuration source. Workspace SSO is separate and remains available. Flowline uses Better Auth's OIDC authorization-code callback at `/api/auth/callback/zitadel`, with state, PKCE S256 and nonce-bound ID-token verification; caller-supplied ID-token sign-in is refused for this provider. Discovery and JWKS are fetched through fixed local metadata routes with guarded outbound requests. The token exchange and userinfo request also use guarded outbound requests. Sign-in does not retain an unused refresh token. The sign-in mapping requires a verified email and matching token and userinfo subject. When `FLOWLINE_BETA_MODE=invite_only`, a new account must qualify through a pending workspace invitation, valid beta access code, configured `FLOWLINE_BETA_ADMINS` signup allowlist, or active platform setup challenge. These paths authorize account creation only; they do not grant workspace membership from an IdP claim. Implicit account linking is disabled while ZITADEL is configured; existing accounts can continue using their existing sign-in method. The Flowline password and TOTP paths remain available.

The isolated test-stack launcher clears these three variables before Next builds or starts, even when the repository `.env` is auto-loaded. Its ZITADEL tests use the test database configuration; workspace SSO remains a separate feature.

Deterministic tests cover the local implementation, and a real development authorization-code callback was verified with the owner-created tenant: a new account reached onboarding and an authenticated workspace. The first attempt hit a user-info connection timeout; a fresh sign-in completed successfully without changing browser protections. Hosted Google login, tenant MFA policy, account recovery and invite enforcement with a real identity remain outstanding. Flowline currently disables provider logout, so Flowline sign-out does not establish that the ZITADEL browser session ended. A separate authenticated account-linking experience for existing accounts is not delivered; owners should not expect a matching email alone to link an old account.

## Owner setup when a no-cost route is verified

1. Check the current ZITADEL Free terms and billing behavior against the aggregate `$0` beta limit before provisioning. Choose the intended data region without adding a card, paid domain or paid option.
2. In the owner-controlled ZITADEL tenant, create a project and a **Web** application using **Authorization Code**, **Basic** client authentication and **PKCE S256**. Follow the [ZITADEL OIDC login guide](https://zitadel.com/docs/guides/integrate/login/oidc/login-users). Register exactly the callback derived from Flowline's trusted `BETTER_AUTH_URL`: `https://<flowline-host>/api/auth/callback/zitadel`. A local HTTP callback is for development or the isolated test environment only; production requires HTTPS.
3. If customers should see Google on the hosted login page, configure and verify Google as an upstream identity provider **inside ZITADEL** using its [Google provider guide](https://zitadel.com/docs/guides/integrate/identity-providers/google). That is distinct from Flowline's existing direct Google sign-in credential; do not label the ZITADEL button as Google until the tenant's Google path is actually configured and checked.
4. As the Flowline operator, set the three `ZITADEL_*` variables in the server's private `.env` (or deployment secret store): the exact HTTPS **issuer origin** outside test mode, Web app Client ID and Client Secret. In test mode only, the issuer may use HTTP when its origin is allowlisted. Keep the client secret out of chat, source control, screenshots and evidence. Environment configuration takes precedence over the optional platform DB configuration; set all three variables together. Changing the issuer or client credentials requires restarting the web processes, and any in-flight sign-in attempt should be treated as expired.
5. Test an invited new identity and an existing account with the real tenant. Check callback, verified email, invitation refusal, workspace isolation, recovery and sign-out. Configure and validate ZITADEL MFA separately from Flowline's local admin TOTP requirement. Keep existing local sign-in available through the pilot.

No new database schema is required. The operator environment tuple is primary; the existing platform-setting and platform-secret tables remain an optional compatibility source. The separate workspace SSO configuration is not a prerequisite for platform sign-in.
