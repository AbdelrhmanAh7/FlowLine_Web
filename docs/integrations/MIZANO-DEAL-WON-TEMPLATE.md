# Template: Deal won → Mizano quote

Issue #149 (part of #144, Mizano connector v1). Gallery id `deal-won-mizano-quote` (`src/engine/design-templates.ts`, "Connected" section; strings under `designTemplates.deal-won-mizano-quote` in `src/i18n/messages/{en,ar}.json`).

Flow: **Deal** (manual trigger with an editable sample deal) → **Deal won?** → **Prepare customer and quote** → **Mizano — Create customer (needs approval)** → **Mizano — Create draft quote** → **Slack — Quote ready**. A deal that is not won ends at "Deal not won" and sends nothing.

- **Approval:** `requireApproval` is on the first Mizano call (`mizano.create_customer`). The worker opens the approval before the action runs, so a pending approval pauses the run (`waiting_approval`) and a rejection fails it (`APPROVAL_REJECTED`) with no call to Mizano and no Slack message. The approval shows the exact customer arguments it is bound to; the quote lines are visible in the "Prepare customer and quote" step output, and the template description says the approval covers the customer details. Showing customer and lines in one approval card needs a preview-capable approval step (not built; **CTO decision on #149, 2026-10-12**, recorded on the issue and in `src/engine/design-templates.ts:275-277`: ship with the one gate on "Create customer", a follow-up tracks an approval that can show arbitrary context).
- **Amounts:** the prepare step formats `qty`, `unitPrice` and `taxRate` as two-decimal strings (`$formatNumber(x, "0.00")`), the shape `mizano.create_draft_quote` accepts.
- **Setup:** choose the Mizano and Slack connections and set `REPLACE_WITH_CHANNEL_ID`. Until a Mizano workspace issues a scoped API key (MZ G5) the Mizano steps are verified with mocks only.
- **Depends on #147** (`mizano.create_customer`, `mizano.create_draft_quote`), which is on `main`, so the template is a normal gallery card with "Use template". The gallery still withholds any template whose actions are missing, so the dependency stays self-healing: the "Connected" grid renders only `availableDesignTemplates`, and withheld templates appear below it in a plain non-card "Not available yet" notice (name + reason, no card, no "Use template" button) under `templateActionIds` / `missingTemplateActions` / `heldBackDesignTemplates` (`src/engine/design-templates.ts`, page `src/app/w/[slug]/templates/page.tsx`, `data-testid="templates-held-back"`). The server backs that up: `createFlow` refuses a withheld template with `409 TEMPLATE_UNAVAILABLE` (`src/server/flows.ts`) and publishing a graph with an unregistered action reports `UNKNOWN_ACTION` → `422 INVALID_FLOW` (`serverIssues`, `src/server/publish.ts`). While the catalog loads only the "Connected" section shows a loading status (the local templates stay usable), and a failed catalog request shows an error with Retry, so no template is offered before the registry is known.

The Slack text reads the customer and line count from the prepare step, not from Mizano's responses, so it does not depend on Mizano echoing the request.

Verification: `tests/integration/deal-won-mizano-approval.test.ts` (the real worker + approval flow with recorders for the two Mizano actions: a recorder replaces the real action when present and inserts a single stand-in when absent, then restores — a dedicated test proves one recorder per id and no leftover; pending approval sends nothing and its preview holds the customer only, approve creates customer then quote then posts to Slack, reject fails with `APPROVAL_REJECTED` and calls nothing; plus the `TEMPLATE_UNAVAILABLE` guard and the `serverIssues` `UNKNOWN_ACTION` check on `customer`/`quote` while the actions are unregistered), `tests/unit/deal-won-mizano-template.test.ts` (engine wiring and data flow with a mocked host: pending, rejected, approved, not won; `templateActionIds` against the **real** provider registry resolves every id the template calls and holds it back while the two Mizano ids are unregistered, and no other template is withheld) and `e2e-army/147-mizano-create-customer-and-quote.e2e.ts` (the #149 tests live in the #147 file because the hub copies only the first 8 top-level `e2e-army/*.e2e.ts` files: the template is listed in EN and AR, as an offered card or, if the registry lacks its actions, in the "Not available yet" notice; a failed catalog shows an error with Retry).

## Acceptance status (issue #149)

- **AC1, gallery listing (EN + AR):** met, `e2e-army/147-mizano-create-customer-and-quote.e2e.ts`. The template is listed by its EN and AR name in both languages. #147 is on `main`, so it is an offered card. If a registry ever lacks its actions it is withheld ("Not available yet", no "Use template"; `createFlow` answers `409 TEMPLATE_UNAVAILABLE`); the registry test (`templateActionIds` against the real provider registry) proves both ends of that contract.
- **AC2, approval blocks; reject ends the run without Mizano calls:** met, verified on the real worker path (`tests/integration/deal-won-mizano-approval.test.ts`). The test replaces the real #147 actions with recorders (and restores them); the real actions' contract is covered by `tests/contract/mizano.test.ts`.
- **AC3, happy-path e2e with a mocked Mizano:** met at worker/engine level (integration test: approve, customer then quote then Slack message; unit test: engine wiring). The browser-level e2e-army happy path (approve in the UI, draft quote at a fake Mizano server) is deferred per the CTO decision on #149 (the throwaway e2e stack has no reachable Mizano workspace, and the fake server must be reachable despite the https-origin rule in `base()`). Not claimed as done at browser level.
- **Approval shows customer + lines:** the approval shows the customer only (**CTO decision on #149, 2026-10-12**, recorded on the issue and in `src/engine/design-templates.ts:275-277`); lines appear in the "Prepare customer and quote" step output. The follow-up for an approval that shows both is tracked outside this PR.
