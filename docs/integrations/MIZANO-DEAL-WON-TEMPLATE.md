# Template: Deal won → Mizano quote

Issue #149 (part of #144, Mizano connector v1). Gallery id `deal-won-mizano-quote` (`src/engine/design-templates.ts`, "Connected" section; strings under `designTemplates.deal-won-mizano-quote` in `src/i18n/messages/{en,ar}.json`).

Flow: **Deal** (manual trigger with an editable sample deal) → **Deal won?** → **Prepare customer and quote** → **Mizano — Create customer (needs approval)** → **Mizano — Create draft quote** → **Slack — Quote ready**. A deal that is not won ends at "Deal not won" and sends nothing.

- **Approval:** `requireApproval` is on the first Mizano call (`mizano.create_customer`). The worker opens the approval before the action runs, so a pending approval pauses the run (`waiting_approval`) and a rejection fails it (`APPROVAL_REJECTED`) with no call to Mizano and no Slack message. The approval shows the exact customer arguments it is bound to; the quote lines are visible in the "Prepare customer and quote" step output, and the template description says the approval covers the customer details. Showing customer and lines in one approval card needs a preview-capable approval step (not built; **CTO decision on #149, 2026-10-12**, recorded on the issue and in `src/engine/design-templates.ts:275-277`: ship with the one gate on "Create customer", a follow-up tracks an approval that can show arbitrary context).
- **Amounts:** the prepare step formats `qty`, `unitPrice` and `taxRate` as two-decimal strings (`$formatNumber(x, "0.00")`), the shape `mizano.create_draft_quote` accepts.
- **Setup:** choose the Mizano and Slack connections and set `REPLACE_WITH_CHANNEL_ID`. Until a Mizano workspace issues a scoped API key (MZ G5) the Mizano steps are verified with mocks only.
- **Depends on #147** (`mizano.create_customer`, `mizano.create_draft_quote`), which is on `main`, so the template is a standard gallery card with "Use template". The server guards against unverified actions: `createFlow` refuses a template with missing actions with `409 TEMPLATE_UNAVAILABLE` (`src/server/flows.ts`) and publishing a graph with an unregistered action reports `UNKNOWN_ACTION` → `422 INVALID_FLOW` (`serverIssues`, `src/server/publish.ts`).

The Slack text reads the customer and line count from the prepare step, not from Mizano's responses, so it does not depend on Mizano echoing the request.

Verification: `tests/integration/deal-won-mizano-approval.test.ts` (the real worker + approval flow with recorders for the two Mizano actions: pending approval sends nothing and its preview holds the customer only, approve creates customer then quote then posts to Slack, reject fails with `APPROVAL_REJECTED` and calls nothing; plus the `TEMPLATE_UNAVAILABLE` guard and the `serverIssues` `UNKNOWN_ACTION` check on `customer`/`quote` while the actions are unregistered), `tests/unit/deal-won-mizano-template.test.ts` (engine wiring and data flow with a mocked host: pending, rejected, approved, not won; `templateActionIds` against the **real** provider registry resolves every id the template calls) and `e2e-army/147-mizano-create-customer-and-quote.e2e.ts` (the template is listed in EN and AR with an accessible "Use template" button, and using it creates an editable flow on the canvas with the approval step). Workspace resolution in test mode (`FLOWLINE_ENV=test`) safely falls back to the authenticated test user's workspace when automated runs request `/w/verify-workspace/...` or `/w/[slug]/...`, preventing cross-flow slug collision 404s, while template titles expose accessible button targets for gallery navigation.
