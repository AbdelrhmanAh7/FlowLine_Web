# Template: Deal won → Mizano quote

Issue #149 (part of #144, Mizano connector v1). Gallery id `deal-won-mizano-quote` (`src/engine/design-templates.ts`, "Connected" section; strings under `designTemplates.deal-won-mizano-quote` in `src/i18n/messages/{en,ar}.json`).

Flow: **Deal** (manual trigger with an editable sample deal) → **Deal won?** → **Prepare customer and quote** → **Mizano — Create customer (needs approval)** → **Mizano — Create draft quote** → **Slack — Quote ready**. A deal that is not won ends at "Deal not won" and sends nothing.

- **Approval:** `requireApproval` is on the first Mizano call (`mizano.create_customer`). The worker opens the approval before the action runs, so a pending approval pauses the run (`waiting_approval`) and a rejection fails it (`APPROVAL_REJECTED`) with no call to Mizano and no Slack message. The approval shows the exact customer arguments it is bound to; the quote lines are visible in the "Prepare customer and quote" step output, and the template description says the approval covers the customer details. Showing customer and lines in one approval card needs a preview-capable approval step (not built; **CTO decision on #149, 2026-10-12**, recorded on the issue and in `src/engine/design-templates.ts:275-277`: ship with the one gate on "Create customer", a follow-up tracks an approval that can show arbitrary context).
- **Amounts:** the prepare step formats `qty`, `unitPrice` and `taxRate` as two-decimal strings (`$formatNumber(x, "0.00")`), the shape `mizano.create_draft_quote` accepts.
- **Setup:** choose the Mizano and Slack connections and set `REPLACE_WITH_CHANNEL_ID`. Until a Mizano workspace issues a scoped API key (MZ G5) the Mizano steps are verified with mocks only.
- **Depends on #147** (`mizano.create_customer`, `mizano.create_draft_quote`). The template ships ahead of its actions, so while they are missing it is **not a gallery entry at all**: the "Connected" grid renders only `availableDesignTemplates`, and the withheld templates appear below it in a plain non-card "Not available yet" notice (name + reason, **no card, no setup checklist, no "Use template" button**) under `templateActionIds` / `missingTemplateActions` / `heldBackDesignTemplates` (`src/engine/design-templates.ts`, page `src/app/w/[slug]/templates/page.tsx`, `data-testid="templates-held-back"`). The server backs that up: `createFlow` refuses it with `409 TEMPLATE_UNAVAILABLE` (`src/server/flows.ts`) and publishing the graph reports `UNKNOWN_ACTION` per unregistered step → `422 INVALID_FLOW` (`serverIssues`, `src/server/publish.ts`). The check is generic and self-healing: any template whose actions are missing is withheld, and it moves into the grid the moment #147 merges, with no change here.

The Slack text reads the customer and line count from the prepare step, not from Mizano's responses, so it does not depend on Mizano echoing the request.

Verification: `tests/integration/deal-won-mizano-approval.test.ts` (the real worker + approval flow with recorders for the two Mizano actions: a recorder replaces the real action when present and inserts a single stand-in when absent, then restores — a dedicated test proves one recorder per id and no leftover; pending approval sends nothing and its preview holds the customer only, approve creates customer then quote then posts to Slack, reject fails with `APPROVAL_REJECTED` and calls nothing; plus the `TEMPLATE_UNAVAILABLE` guard and the `serverIssues` `UNKNOWN_ACTION` check on `customer`/`quote` while the actions are unregistered), `tests/unit/deal-won-mizano-template.test.ts` (engine wiring and data flow with a mocked host: pending, rejected, approved, not won; `templateActionIds` against the **real** provider registry resolves every id the template calls and holds it back while the two Mizano ids are unregistered, and no other template is withheld) and `e2e-army/149-deal-won-mizano-quote.e2e.ts` (the template is listed in EN and AR in the non-card "Not available yet" notice; Use is covered by the integration test because it is not offered until #147).
