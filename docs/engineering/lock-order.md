# Lock order

Two transactions that lock the same rows in opposite orders can deadlock, and PostgreSQL then aborts one of them (SQLSTATE `40P01`). Issue #37 was such a deadlock between `confirmSsoLink` and `completeFederatedChallenge`; its fix is `lockUserThenSessions` in `src/server/federated-locks.ts`.

This page lists the seven lockable entities that the account, membership and SSO transactions share, ranked in the order a transaction takes them. The federated authority paths follow the more detailed rule in [FEDERATED_MFA.md](../security/FEDERATED_MFA.md#lock-order), pinned by `tests/unit/federated-lock-order.test.ts`; this page does not replace it. Rows that name a documented exception describe code that goes backward on purpose and state why it cannot deadlock; `tests/unit/lock-order-doc.test.ts` pins the rank order and that each exception stays written down. The table covers explicit locks and the writes of the listed files; implicit locks from cascades and foreign keys are covered only where a row says so.

## Entities and global order

Intended rule: take lower ranks first and do not return to a lower rank. The rank order is the one the federated and email-token code follows; code that deviates is marked **Documented exception** with its reason. Before rank 1 a flow may take its own pending-state `verification` row, and `delete` takes the retained-file accounting lock (`lockRetainedFileAccounting`, `src/server/retained-files.ts`); neither is one of the seven entities. Deliberate exceptions (the reset's account-before-session writes, the audit insert's key-share on the workspace, and `delete`'s audit rows before its workspace locks) are written into ranks 4, 5 and 7 with the reason each cannot deadlock.

| Rank | Entity | Table | Locked in | Notes |
|---|---|---|---|---|
| 1 | User | `user` | `src/server/federated-locks.ts` (`lockUserThenSessions`); `src/server/sso.ts` callbacks (`FOR SHARE`); `src/server/email/flows.ts` (`consumeAccountToken`, `FOR UPDATE`, after the retained-file accounting lock for `delete`) | The user row is the first row lock of every flow here (federated flows lock their own pending `verification` row before it, [FEDERATED_MFA.md](../security/FEDERATED_MFA.md#lock-order)). Issue #45 moved it ahead of the email token; this is the order that prevents the reset/delete deadlock. |
| 2 | Email token | `email_token` | `src/server/email/flows.ts` (`consumeAccountToken`, `FOR UPDATE`) | Always second, after the user ([email-token order](../security/FEDERATED_MFA.md#email-token-lock-order)). No federated flow locks it. |
| 3 | Session | `session` | `src/server/federated-locks.ts`; `src/server/sso.ts`; `src/server/email/flows.ts` (`reset`: `DELETE` of the user's sessions) | The transaction's own or unissued session first, then the bound (initiating) session. |
| 4 | Account | `account` | `src/server/federated-mfa.ts`, `src/server/sso-link.ts` (`FOR SHARE`); `src/server/email/flows.ts` (`reset`: credential write, then the `sso:` links) | Documented exception: `consumeAccountToken("reset")` writes account **before** session (rank 4 before rank 3); #45 did not reorder these writes, it only put the user lock in front of them. It cannot form a cycle because every transaction that locks session or account rows of a user locks that user row first, and the reset holds it `FOR UPDATE`. A new code path that locks session or account rows without the user row first must not rely on this. |
| 5 | Workspace | `workspace` | `src/server/members.ts` (`changeRole`, `removeMember` through `lockWorkspaceMembership`, `FOR NO KEY UPDATE`); `src/server/email/flows.ts` (`delete`: every workspace of the user, ordered by id, `FOR UPDATE`, after the user and token) | Member changes take it before the member row (rank 6) and take no user lock. The `audit_event` insert (rank 7) key-share locks this row after the SSO transactions hold their member row, which is backward (rank 6 then rank 5): a documented exception that is safe only because member changes use `FOR NO KEY UPDATE`, which does not conflict with `FOR KEY SHARE` ([workspace row rule](../security/FEDERATED_MFA.md#lock-order), issue #42). `FOR UPDATE` here would deadlock again. Account deletion keeps `FOR UPDATE`; it holds the user `FOR UPDATE` first, which the SSO transactions need before their member row, so they cannot interleave (issue #45). Since #109 `delete` also inserts its `account.deleted` audit rows (rank 7) before it locks the workspaces, which the retained-file accounting lock serializes ([example](#workspace-for-update-vs-sso-audit-insert-47)). |
| 6 | Member | `workspace_member` | `src/server/sso-link.ts`, `src/server/sso.ts` (`FOR UPDATE` or `FOR SHARE`); `src/server/federated-mfa.ts` (`FOR SHARE`); `src/server/members.ts` (row updated or deleted after the workspace lock) | Taken after `sso_config` in the SSO paths. The `src/server/sso.ts` callbacks also share-lock the provider link row (account, rank 4) after the member row: a second documented backward step, covered by the user row held `FOR SHARE` first. Read from the code, not reproduced; a path that locks that account row `FOR UPDATE` without the user row first would form a cycle, tracked in [#241](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/241) (part of [#192](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/192)). |
| 7 | Audit | `audit_event` | `src/server/audit.ts` (`audit()` insert), called last by `src/server/sso-link.ts`, `src/server/federated-mfa.ts`, `src/server/sso.ts` and `src/server/members.ts` | The insert key-share locks its `workspace` row (rank 5); see the rank 5 exception. `consumeAccountToken("delete")` in `src/server/email/flows.ts` also inserts it, before its workspace locks (rank 5 note). |

## Known violations

These known violations of the global lock order were identified in the PR #128 review (tracked via #192). Each represents an existing code path that departs from monotonic rank order and risks a `40P01` deadlock against concurrent transactions.

| Violation | Code | Ranks (taken order) | Deadlock pair | Tracking |
|---|---|---|---|---|
| V1 (resolved) | `src/server/audit.ts` (`audit()`, called last by `src/server/sso-link.ts`, `src/server/federated-mfa.ts` and `src/server/sso.ts`) | Workspace key-share (5) → Member (6) → SSO audit insert (7) | Resolved by #42: `changeRole` and `removeMember` in `src/server/members.ts` lock `workspace` (5) `FOR NO KEY UPDATE` before `workspace_member` (6); does not conflict with audit insert's `FOR KEY SHARE`. | Closed by [#42](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/42) |
| V2 | `src/server/sso.ts` (`completeSso` callbacks, MFA and non-MFA paths) | Member (6) → Account (4) (share-locks provider link `account` row after `workspace_member`: taken order 6 → 4) | Any concurrent transaction that locks `account` (rank 4, `FOR UPDATE`) before `workspace_member` (rank 6) | [#241](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/241) (part of [#192](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/192)) |

## Review checklist for a new transaction

- [ ] List every row it locks: explicit `.for("update")`/`.for("share")`, rows changed by `UPDATE`/`DELETE`, and rows an `INSERT` references through a foreign key (`audit_event.workspace_id` → `workspace` in `src/db/schema.ts`).
- [ ] Take them in rank order and never return to a lower rank. A new deviation is a bug unless it is added to the table as a known gap with its own issue.
- [ ] Lock several rows of one table in a deterministic order (`orderBy` id), as `consumeAccountToken("delete")` does for workspaces.
- [ ] Use `FOR UPDATE` only for rows the transaction writes; read-only fences use `FOR SHARE`, as the `src/server/sso.ts` callbacks do.
- [ ] Federated authority rows (user, sessions, factor, accounts, tenant authority) follow [FEDERATED_MFA.md](../security/FEDERATED_MFA.md#lock-order) and take the user and sessions through `lockUserThenSessions`.
- [ ] Pin the statement order in a test (pattern: `tests/unit/federated-lock-order.test.ts`); a new pair of conflicting paths also gets a two-connection test (pattern: `tests/integration/federated-lock-order.test.ts`).
- [ ] Update this table, and FEDERATED_MFA.md for federated paths, in the same PR as the change.

## Worked examples

### Example #41: password reset vs SSO link confirmation ([#41](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/41))

**Hazard (before #45 and #41):** `consumeAccountToken("reset")` in `src/server/email/flows.ts` wrote the credential `account` row (rank 4), deleted the user's `session` rows (rank 3), then updated the `user` row (rank 1), while `confirmSsoLink` in `src/server/sso-link.ts` locks user (rank 1), session (rank 3), account (rank 4) in that order. Interleaved, reset held the account row and waited for a session that link confirmation held, which waited for the account row: account → session → user against user → session → account.

**Ordering rule:** user (1) → token (2) → session (3) → account (4), the same order as `confirmSsoLink` (`src/server/sso-link.ts`, via `lockUserThenSessions` in `src/server/federated-locks.ts`). Implemented in `consumeAccountToken` in `src/server/email/flows.ts`: PR #65 (#45) established taking the user row `FOR UPDATE` before the token row; issue #41 (commit `66cc2799`) moved session deletion before credential account writes, completing the strict rank order. A second reset or a link confirmation for the same user queues at the user row and cannot hold a lower-ranked row first. Pinned by `tests/unit/email-token-lock-order.test.ts`, `tests/integration/email-token-lock-order.test.ts`, `tests/unit/password-reset-lock-order.test.ts`, and `tests/integration/password-reset-lock-order.test.ts`.

### Example #42: member role change vs SSO audit ([#42](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/42))

**Hazard (before #42):** `changeRole` (or `removeMember`) in `src/server/members.ts` locked the `workspace` row `FOR UPDATE` (rank 5), then wrote the member row (rank 6). SSO transactions (`confirmSsoLink`, `src/server/sso-link.ts` and callbacks in `src/server/sso.ts`, `src/server/federated-mfa.ts`) lock that member row (rank 6, `FOR UPDATE` or `FOR SHARE`), then `audit()` in `src/server/audit.ts` inserts an `audit_event` row (rank 7) that takes a key-share lock on the same `workspace` row (rank 5). Each held the row the other needed next, so one aborted with `40P01`.

**Ordering rule:** workspace (5) → member (6) → audit (7), with the workspace lock taken `FOR NO KEY UPDATE`. The SSO paths still reach back from the audit insert to the workspace row (a documented exception, see rank 5), and that is safe because `FOR NO KEY UPDATE` does not conflict with `FOR KEY SHARE`, so the insert never waits for a member change. Implemented in `lockWorkspaceMembership` (`src/server/members.ts`), pinned by `tests/unit/member-lock-order.test.ts` and `tests/integration/member-lock-order.test.ts`.

### Email token vs user delete ([#45](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/45))

- **Hazard:** `email_token.user_id` is `ON DELETE SET NULL` (`src/db/schema.ts`), so deleting a user updates every token row of that user after the user row is locked. When `consumeAccountToken` locked its own token row first, a password reset and a delete confirmation of one user could deadlock, and two resets with different tokens each held their own token while queueing at the user row.
- **Rule:** lock the user row `FOR UPDATE`, then the token row `FOR UPDATE`, then (`delete`) the user's workspaces ordered by id; `delete` takes the retained-file accounting lock (`lockRetainedFileAccounting`, `src/server/retained-files.ts`) before all of them. Code that writes `email_token` rows of an existing user locks the user first. This is the table's order (user rank 1, token rank 2, workspace rank 5), so it needs no exception; the detailed rule is in [FEDERATED_MFA.md](../security/FEDERATED_MFA.md#email-token-lock-order).
- **Code:** `consumeAccountToken` in `src/server/email/flows.ts` (fixed by PR #65), pinned by `tests/unit/email-token-lock-order.test.ts` and `tests/integration/email-token-lock-order.test.ts`.

### Workspace `FOR UPDATE` vs SSO audit insert ([#47](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/47))

- **Hazard:** `consumeAccountToken("delete")` locks every workspace of the user `FOR UPDATE` and later deletes the user. The SSO callback transactions in `completeSso` (`src/server/sso.ts`) share-lock the user first and call `audit()` (`src/server/audit.ts`) last; its `audit_event` insert key-share locks the same `workspace` row. A deletion that held workspace W before taking the user row (workspace rank 5, then user rank 1: backward) could wait for the user while the SSO transaction held the user `FOR SHARE` and waited for W, the same cycle as #42.
- **Rule:** a transaction that locks a user's workspaces `FOR UPDATE` takes that user's row first and never waits for it while holding W. Deletion keeps `FOR UPDATE` on the workspaces because sole-member workspaces are deleted with the account (`tests/integration/retained-file-locking.test.ts`).
- **Code:** since PR #65, `consumeAccountToken` in `src/server/email/flows.ts` locks the user row before the workspaces, so, read from the code on main, this pair no longer forms the cycle. Since #109 the deletion also takes the SSO transaction's own order: user row, then the `audit_event` insert (key-share on each workspace), then the workspaces `FOR UPDATE` (ordered by id), so it never waits for a key-share while holding W. The audit rows are written from a membership read taken under the user lock (no membership of the user can be added while that row is held); under the workspace lock they are corrected if a role changed or a membership was removed in between, rows of sole-member workspaces go with the workspace (`ON DELETE CASCADE`), and `transfer_required` now rolls the transaction back so no audit row survives a refused deletion. The audit insert key-shares W before the deletion asks for W `FOR UPDATE`, so two deletions in one workspace that both reached that point would each wait for the other's key-share (`40P01`). They cannot: every deletion takes the installation-wide retained-file accounting lock (`lockRetainedFileAccounting`, a `pg_advisory_xact_lock` plus the singleton counter row `FOR UPDATE`) as its first statement, so deletions run one at a time; every other `workspace` `FOR UPDATE` (`runs.ts`, `agents.ts`) comes before that transaction's first write that key-shares W. Pinned by `tests/unit/email-token-lock-order.test.ts` (statement order, mocked database), `tests/integration/email.test.ts` (rollback on `transfer_required`, one record after the deletion) and `tests/integration/retained-file-locking.test.ts` (two co-members deleting at once on two real connections: the second waits at the accounting lock and both finish). The upgrade the reorder could introduce is pinned negatively by `tests/integration/account-delete-key-share-upgrade.test.ts`: with only the accounting lock removed (a test-only mock), the same two deletions, each paused after its audit insert and released together, leave one aborted with `40P01` at the workspace `FOR UPDATE` while holding its key-share — so the accounting lock is load-bearing, not decorative. The deletion-vs-SSO race is covered by the #108 test (`tests/integration/account-delete-sso-lock-order.test.ts`, now part of this change together with the `routeTransactions` helper in `tests/integration/pg-lock-helpers.ts`): deletion vs the user's own SSO sign-in in flight, in both orders, on two real connections, both finishing without `40P01`.
