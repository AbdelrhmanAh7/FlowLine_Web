# Lock order

Two transactions that lock the same rows in opposite orders can deadlock, and PostgreSQL then aborts one of them (SQLSTATE `40P01`). Issue #37 was such a deadlock between `confirmSsoLink` and `completeFederatedChallenge`; its fix is `lockUserThenSessions` in `src/server/federated-locks.ts`.

This page lists the seven lockable entities that the account, membership and SSO transactions share, ranked in the order a transaction takes them. The federated authority paths follow the more detailed rule in [FEDERATED_MFA.md](../security/FEDERATED_MFA.md#lock-order), pinned by `tests/unit/federated-lock-order.test.ts`; this page does not replace it. Rows that mention a known gap describe existing code that does not follow the order yet. The table covers explicit locks and the writes of the listed files; implicit locks from cascades and foreign keys are covered only where a row says so.

## Entities and global order

Intended rule: take lower ranks first and do not return to a lower rank. The rank order is the one the federated and email-token code follows; code that deviates is marked **Known gap**. Before rank 1 a flow may take its own pending-state `verification` row, and `delete` takes the retained-file accounting lock (`lockRetainedFileAccounting`, `src/server/retained-files.ts`); neither is one of the seven entities. The only deliberate exception to the rule is `delete` (audit rows, then workspaces), see rank 6.

| Rank | Entity | Table | Locked in | Notes |
|---|---|---|---|---|
| 1 | User | `user` | `src/server/federated-locks.ts` (`lockUserThenSessions`); `src/server/sso.ts` callbacks (`FOR SHARE`); `src/server/email/flows.ts` (`consumeAccountToken`, `FOR UPDATE`) | Every path that locks a user row takes it before the rows below. `consumeAccountToken("delete")` deletes it last. |
| 2 | Email token | `email_token` | `src/server/email/flows.ts` (`consumeAccountToken`, `FOR UPDATE`) | Taken after the user row; the token is re-read under both locks ([FEDERATED_MFA.md](../security/FEDERATED_MFA.md#email-token-lock-order)). |
| 3 | Session | `session` | `src/server/federated-locks.ts`; `src/server/sso.ts` | The transaction's own or unissued session first, then the bound (initiating) session. |
| 4 | Account | `account` | `src/server/federated-mfa.ts`, `src/server/sso-link.ts` (`FOR SHARE`); `src/server/email/flows.ts` (`consumeAccountToken("reset")`, writes) | The reset writes account and session rows while it holds the user row `FOR UPDATE`, so no other user-first path interleaves. Known gap ([#241](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/241), part of [#192](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/192)): the `src/server/sso.ts` callbacks share-lock the provider link row after the member row (rank 5). |
| 5 | Member | `workspace_member` | `src/server/sso-link.ts`, `src/server/sso.ts` (`FOR UPDATE` or `FOR SHARE`); `src/server/federated-mfa.ts` (`FOR SHARE`); `src/server/members.ts` (`changeRole`, `removeMember`, writes) | SSO paths take it after `sso_config`. Known gap ([#42](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/42)): `changeRole` and `removeMember` write it after the workspace row (rank 6). |
| 6 | Workspace | `workspace` | `src/server/members.ts` (`changeRole`, `removeMember`, `FOR UPDATE`); `src/server/email/flows.ts` (`delete`: every workspace of the user, ordered by id, after its `account.deleted` audit rows); key-share lock by the `audit_event` insert | The `audit_event.workspace_id` foreign key (`src/db/schema.ts`) makes every `audit()` insert key-share lock this row. Deliberate exception (#109): `delete` inserts its audit rows (rank 7) before it locks the workspaces `FOR UPDATE`, which the retained-file accounting lock serializes ([example](#workspace-for-update-vs-sso-audit-insert-47)). |
| 7 | SSO audit | `audit_event` | `src/server/audit.ts` (`audit()` insert), called last by `src/server/sso-link.ts`, `src/server/federated-mfa.ts` and `src/server/sso.ts` | Follows the order in the SSO paths (member, then workspace key-share, then audit). The deadlock with `changeRole`/`removeMember` is the rank 5 gap. `consumeAccountToken("delete")` in `src/server/email/flows.ts` also inserts it, before its workspace locks (rank 6 note). |

## Review checklist for a new transaction

- [ ] List every row it locks: explicit `.for("update")`/`.for("share")`, rows changed by `UPDATE`/`DELETE`, and rows an `INSERT` references through a foreign key (`audit_event.workspace_id` → `workspace` in `src/db/schema.ts`).
- [ ] Take them in rank order and never return to a lower rank. A new deviation is a bug unless it is added to the table as a known gap with its own issue.
- [ ] Lock several rows of one table in a deterministic order (`orderBy` id), as `consumeAccountToken("delete")` does for workspaces.
- [ ] Use `FOR UPDATE` only for rows the transaction writes; read-only fences use `FOR SHARE`, as the `src/server/sso.ts` callbacks do.
- [ ] Federated authority rows (user, sessions, factor, accounts, tenant authority) follow [FEDERATED_MFA.md](../security/FEDERATED_MFA.md#lock-order) and take the user and sessions through `lockUserThenSessions`.
- [ ] Pin the statement order in a test (pattern: `tests/unit/federated-lock-order.test.ts`); a new pair of conflicting paths also gets a two-connection test (pattern: `tests/integration/federated-lock-order.test.ts`).
- [ ] Update this table, and FEDERATED_MFA.md for federated paths, in the same PR as the change.

## Worked examples

### Example #41: password reset vs SSO link confirmation ([#41](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/41))

**Hazard (before #45 and #41):** `consumeAccountToken("reset")` in `src/server/email/flows.ts` wrote the credential `account` row (rank 4), deleted the user's `session` rows (rank 3), then updated the `user` row (rank 1), while `confirmSsoLink` in `src/server/sso-link.ts` locks user (rank 1), session (rank 3), account (rank 4) in that order. Interleaved, reset held the account row and waited for a session that link confirmation held, which waited for the account row: account → session → user against user → session → account.

**Ordering rule:** user (1) → token (2) → session (3) → account (4), the same order as `confirmSsoLink` (`src/server/sso-link.ts`, via `lockUserThenSessions` in `src/server/federated-locks.ts`). Implemented in `consumeAccountToken` in `src/server/email/flows.ts`: PR #65 (#45) established taking the user row `FOR UPDATE` before the token row; issue #41 (commit `66cc2799`) moved session deletion before credential account writes, completing the strict rank order. A second reset or a link confirmation for the same user queues at the user row and cannot hold a lower-ranked row first. Pinned by `tests/unit/email-token-lock-order.test.ts`, `tests/integration/email-token-lock-order.test.ts`, `tests/unit/password-reset-lock-order.test.ts`, and `tests/integration/password-reset-lock-order.test.ts`.

### Example #42: member role change vs SSO audit ([#42](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/42))

**Hazard:** `changeRole` (or `removeMember`) in `src/server/members.ts` locks the `workspace` row `FOR UPDATE` (rank 6), then writes the member row (rank 5). SSO transactions (`confirmSsoLink`, `src/server/sso-link.ts` and callbacks in `src/server/sso.ts`, `src/server/federated-mfa.ts`) lock that member row (rank 5, `FOR UPDATE` or `FOR SHARE`), then `audit()` in `src/server/audit.ts` inserts an `audit_event` row (rank 7) that takes a key-share lock on the same `workspace` row (rank 6). Each holds the row the other needs next, so one aborts with `40P01`.

**Ordering rule:** member (5) → workspace (6) → audit (7): the SSO paths follow it. `changeRole` and `removeMember` take the workspace before the member row, so they are the known gap: **pending #42** (known gap in [FEDERATED_MFA.md](../security/FEDERATED_MFA.md#lock-order); the rank 5 note above).

### Email token vs user delete ([#45](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/45))

- **Hazard:** `email_token.user_id` is `ON DELETE SET NULL` (`src/db/schema.ts`), so deleting a user updates every token row of that user after the user row is locked. When `consumeAccountToken` locked its own token row first, a password reset and a delete confirmation of one user could deadlock, and two resets with different tokens each held their own token while queueing at the user row.
- **Rule:** lock the user row `FOR UPDATE`, then the token row `FOR UPDATE`, then (`delete`) the user's workspaces ordered by id; `delete` takes the retained-file accounting lock (`lockRetainedFileAccounting`, `src/server/retained-files.ts`) before all of them. Code that writes `email_token` rows of an existing user locks the user first. This follows the rank order (user 1, token 2, workspaces 6); the detailed rule is in [FEDERATED_MFA.md](../security/FEDERATED_MFA.md#email-token-lock-order).
- **Code:** `consumeAccountToken` in `src/server/email/flows.ts` (fixed by PR #65), pinned by `tests/unit/email-token-lock-order.test.ts` and `tests/integration/email-token-lock-order.test.ts`.

### Workspace `FOR UPDATE` vs SSO audit insert ([#47](https://github.com/AbdelrhmanAh7/FlowLine_Web/issues/47))

- **Hazard:** `consumeAccountToken("delete")` locks every workspace of the user `FOR UPDATE` and later deletes the user. The SSO callback transactions in `completeSso` (`src/server/sso.ts`) share-lock the user first and call `audit()` (`src/server/audit.ts`) last; its `audit_event` insert key-share locks the same `workspace` row. A deletion that held workspace W before taking the user row (workspace, rank 6, before user, rank 1) could wait for the user while the SSO transaction held the user `FOR SHARE` and waited for W, the same cycle as #42.
- **Rule:** a transaction that locks a user's workspaces `FOR UPDATE` takes that user's row first and never waits for it while holding W. Deletion keeps `FOR UPDATE` on the workspaces because sole-member workspaces are deleted with the account (`tests/integration/retained-file-locking.test.ts`).
- **Code:** since PR #65, `consumeAccountToken` in `src/server/email/flows.ts` locks the user row before the workspaces, so, read from the code on main, this pair no longer forms the cycle. Since #109 the deletion also takes the SSO transaction's own order: user row, then the `audit_event` insert (key-share on each workspace), then the workspaces `FOR UPDATE` (ordered by id), so it never waits for a key-share while holding W. The audit rows are written from a membership read taken under the user lock (no membership of the user can be added while that row is held); under the workspace lock they are corrected if a role changed or a membership was removed in between, rows of sole-member workspaces go with the workspace (`ON DELETE CASCADE`), and `transfer_required` now rolls the transaction back so no audit row survives a refused deletion. The audit insert key-shares W before the deletion asks for W `FOR UPDATE`, so two deletions in one workspace that both reached that point would each wait for the other's key-share (`40P01`). They cannot: every deletion takes the installation-wide retained-file accounting lock (`lockRetainedFileAccounting`, a `pg_advisory_xact_lock` plus the singleton counter row `FOR UPDATE`) as its first statement, so deletions run one at a time; every other `workspace` `FOR UPDATE` (`members.ts`, `runs.ts`, `agents.ts`) comes before that transaction's first write that key-shares W. Pinned by `tests/unit/email-token-lock-order.test.ts` (statement order, mocked database), `tests/integration/email.test.ts` (rollback on `transfer_required`, one record after the deletion) and `tests/integration/retained-file-locking.test.ts` (two co-members deleting at once on two real connections: the second waits at the accounting lock and both finish). The upgrade the reorder could introduce is pinned negatively by `tests/integration/account-delete-key-share-upgrade.test.ts`: with only the accounting lock removed (a test-only mock), the same two deletions, each paused after its audit insert and released together, leave one aborted with `40P01` at the workspace `FOR UPDATE` while holding its key-share — so the accounting lock is load-bearing, not decorative. The deletion-vs-SSO race is covered by the #108 test (`tests/integration/account-delete-sso-lock-order.test.ts`, now part of this change together with the `routeTransactions` helper in `tests/integration/pg-lock-helpers.ts`): deletion vs the user's own SSO sign-in in flight, in both orders, on two real connections, both finishing without `40P01`.
