# Flowline Phase 1 — agent-driven exploratory test

## Environment and method

- Tested `http://localhost:3100`, the already running `FLOWLINE_ENV=test` stack, with Git HEAD `edeb6a8` on 2026-09-27. I did not start or stop the app or Docker, edit product code, or commit.
- Browser-control discovery found the computer-use browser plugin and installed Playwright. **Used Playwright**, `@playwright/test` 1.63.0 with real Chromium 153.0.8010.12, headless on Windows. All UI actions used clicks, typing, key presses, drags, and browser navigation. Only the documented `/api/test/faults` endpoint was called directly. Network delays were used to expose loading and saving states.
- Ran 11 scripts sequentially with one Chromium process at a time (the conflict test used two contexts in one process). Evidence: 89 screenshots in [`screenshots/`](screenshots/) and scripts in [`scripts/`](scripts/). Reviewed the application areas in design slides 05–15, plus the token and responsive references in slides 03, 04, and 14.
- Tested one newly signed-up account plus the supplied account B; seven widths (1440, 1280, 1279, 1024, 768, 767, 375). Observed five run attempts: successful, failed, failed re-run, successful re-run, and a mobile run. Browser event logs are in the JSON evidence files in this folder. The eight 500 responses were injected save/load faults; three 404 responses were intentional cross-tenant probes; one 409 was the expected edit conflict. No unprovoked page errors or network failures were observed in the completed normal paths.

## Paths that worked

- Landing → sign-up → all three onboarding steps → template builder → Run → inspector. The separate **Skip setup** path reached an empty dashboard. A blank flow showed the trigger empty state.
- Palette click, palette drag, and `/` search added nodes; handle drags connected nodes. A duplicate connection was rejected with “already has an input” and the edge count stayed at four. Duplicate, Delete, undo, redo, Esc, keyboard input guards, zoom, Fit, Ctrl+0, and drawer-field persistence responded. The blank-flow interaction screenshots are from an unsaved session; persistence was verified on the template flow after waiting for Saved.
- The transform expression `$number("x")` produced a failed run with downstream steps skipped. Inspector Input, Output, and Error tabs showed the corresponding payload/error; “Re-run from this step” reused the upstream trigger. Repairing the expression through the drawer and re-running produced a successful run. Failed filter, search-empty state, and Clear filters worked.
- Autosave showed **Unsaved → Saving → Saved**. Injected save failures showed **Failed to save — retrying**, then manual Retry and Saved. Injected load failures retained the shell, showed an error, and recovered with Retry. Loading used an in-region skeleton rather than a full-screen spinner. See [autosave](screenshots/autosave-saving.png), [save failure](screenshots/state-save-failed.png), [load error](screenshots/state-load-error.png), and [loading skeleton](screenshots/misc-loading-skeleton.png).
- Offline editing showed a persistent banner, kept the draft locally, and disabled Run with an explanation. Reconnect saved it. When another UI session changed the server copy meanwhile, the first session showed a conflict, disabled Run, and resolved via **Keep my version**; the other session saw the resolution after reload. See [offline](screenshots/state-offline.png) and [conflict](screenshots/conflict-banner.png).
- Account B could not see account A's flows, open A's workspace, open A's flow under B's workspace, or load A's run by URL. See [foreign flow](screenshots/tenancy-b-a-flow.png) and [foreign run](screenshots/tenancy-b-a-run.png).
- At the seven tested widths, the builder had no document-level horizontal scroll. Sidebar widths were 240px at 1440/1280, 48px at 1279/1024/768, and hidden at 767/375. The 360px desktop/tablet drawer and mobile monitor-only banner appeared. Mobile could start and observe a run. Inter Variable, app background `rgb(9,9,11)`, sidebar surface `rgb(17,17,19)`, and 240px desktop sidebar matched the design tokens. The sampled Run button had no hover translation, and reduced-motion emulation reduced animation/transition durations to near zero.
- Integrations, unavailable templates, API keys, and billing explained their Phase 2/3 or unmetered preview status rather than claiming live connectors, keys, charges, or usage. The tested disabled Connect control had `aria-disabled="true"` and explanatory text.

## Coverage limits

- This was exploratory sampling, not an exhaustive button or accessibility audit. I did not complete every invalid connection variant (self, loop, into trigger, out of output), multi-select, Backspace as a canvas delete key, every settings action, or responsive checks for every non-builder page.
- The initial auth hydration warning arose only when an early Playwright screenshot hid the caret during hydration; normal journeys and later sessions had no corresponding console error. It is excluded from findings.
- Product scope differs from some slide mock content: live integrations, LLM nodes, billing, and API keys are explicitly marked as future phases in the UI. Visual comparison was against the application area inside each slide's mock frame, not the slide title or frame.
