## Actual Paddle implementation requirements

`src/billing/paddle.ts` creates customers, creates transactions, retrieves/updates/cancels subscriptions. Minimum runtime permissions derive from those operations: `customer.write`, `transaction.write`, `subscription.write`. Price/product write, notification write and account-wide access are not required by this adapter. Dashboard setup can create fixtures and notification destinations independently. [Permission model](https://developer.paddle.com/api-reference/about/permissions/), [create customer](https://developer.paddle.com/api-reference/customers/create-customer/), [create transaction](https://developer.paddle.com/api-reference/transactions/create-transaction/), [update subscription](https://developer.paddle.com/api-reference/subscriptions/update-subscription/).

- Checkout: `<FLOWLINE_PUBLIC_URL>/billing/checkout?ws=<actual-workspace-slug>`. Paddle appends `_ptxn`; Flowline loads Paddle.js and opens the overlay. Register the actual default payment link; catalog trials are defined on the price, not merely in plan metadata.
- Return pages: `/w/<actual-slug>/settings?billing=success` and `?billing=cancelled`.
- Webhook: `<approved-reachable-public-origin>/api/billing/webhook`, POST with `Paddle-Signature`. Code rejects invalid/stale signatures and deduplicates event IDs. Keep this route reachable without a blanket interactive login challenge.
- Adapter handles `transaction.completed`; subscription lifecycle (`created`, `updated`, `activated`, `trialing`, `paused`, `resumed`, `canceled`, `past_due`); adjustment created/updated. Subscribe to the implemented sandbox events needed for the journey. Record actual selected event list and destination ID.
- A real sandbox checkout plus subscription state, signed notification, duplicate delivery and reconciliation is required. A simulator or successful key probe cannot substitute for checkout.

## Bootstrap and owner stop points

Operator bootstrap issues an email-bound challenge, expiring after 30 minutes and stored only as a hash. `/admin/setup` redeems it through a masked POST field into a narrow setup session. If no real email is configured, the setup session accepts Provider, From and API key, then limits delivery to that bound identity until setup completes. Bound user must sign in/sign up, consume the real verification link and enroll TOTP; completing setup consumes the challenge and closes bootstrap atomically. Later `/admin` writes require MFA step-up. Test/staging outbox is a separate local testing mode, never evidence of external email delivery.

Stop affected browser control and recording for login/MFA/CAPTCHA, secret creation/entry, sensitive consent and business/policy attestations. Ask the owner to enter/store these directly and reply done; never dump secret dialogs, QR codes, seeds, recovery codes, cookies, tokens or keys. The latest client-creation done reply is not authorization for paid usage, domain purchase, DNS, host access or deployment.

Exact sending-domain DNS values must come from the actual provider dashboard after owner-approved domain discovery. Preserve unrelated MX/TXT/SPF/DKIM records; do not add multiple conflicting SPF records. Domain purchase is blocked by the $0 cap. Pi read-only approval comes before inspection; deployment/exposure approval must subsequently include SHA/digest/architecture, exact services/DNS/tunnel, backup/rollback and $0 expected cost.

## Resend probe mismatch and bounded correction

Original current source `src/server/platform-probes.ts` probes Resend with `GET /domains` and labels every 401/403 rejected. Official error documentation distinguishes a **401** `restricted_api_key` with the message that the key can only send email, from a **403** `restricted_api_key` indicating inactive key and a 403 `suspended_api_key`. Sending-only credentials can therefore receive a false rejection from a management endpoint. Do not widen key access or turn a denied management request into a verification PASS. Real send verification already exists in `src/server/email/config.ts` for the exact saved revision. [Official errors](https://resend.com/docs/api-reference/errors).

Narrow correction now implemented: only the exact documented sending-only 401 returns `insufficient_permissions`, with warning copy in Arabic/English. It preserves status/verification metadata and audits unverified; every 403 remains rejected. No automatic email send or key-permission widening. Focused mocked-network unit suite passed 14/14 in a primary-granted single-worker test window. See [validation and precise scope](RESEND_PROBE_VALIDATION.md) and [cp21-relative patch](RESEND_PROBE_CHANGE.patch). No live key or provider request was used. Current frozen local runtime cp21 predates the correction; later candidate freeze/gates/rebuild are required before claims about updated runtime behavior.
