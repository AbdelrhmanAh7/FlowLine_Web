# Retained upload admission — M5 partial scope

Candidate branch `codex/paid-pilot-upload-admission-20261003`, exact base `a9f7597c90b98128a1cebf46a949810e0586c31d`. On 2026-10-03 the branch was rebased onto #16 head `b63ffed` (three additive i18n conflicts, migration still `0024`); the focused evidence below predates that rebase and records the old base. This adds shared admission for retained `file_object.data` bytes across knowledge/pasted sources, the file-upload API and Company Builder's approved-information fixtures. All three production file insertion sites use `insertRetainedFile` inside their existing or new database transaction. Existing access checks are preserved.

Admission retains the installation advisory lock to coordinate with pre-counter upload writers, then locks the installation counter row followed by the workspace counter row under the current callers' default READ COMMITTED isolation. Both reads use primary-key lookups; no retained-file scan remains. A database trigger maintains raw bytes (`octet_length(data)`, independent of size metadata) and file counts on insert, delete and changes to data/workspace. File and counters commit or roll back together. Triggers also cover direct SQL and workspace cascades, including account deletion's sole-member workspaces; workspace counters themselves cascade away. A deleted knowledge source deletes its retained file and frees capacity. Successful upload responses expose only file id/name/mime/size.

Operational defaults are **100 MiB of retained raw file bytes per workspace** and **512 MiB across this database installation**. Operators can explicitly set positive integer byte limits with `FLOWLINE_UPLOAD_WORKSPACE_MAX_BYTES` and `FLOWLINE_UPLOAD_INSTALLATION_MAX_BYTES`, consistently across processes using this database. Invalid configuration or a missing installation counter fails closed with a translated 503. These are storage circuit breakers, not subscription promises, pricing or installed pilot entitlements. Existing content above a lowered limit remains intact; further uploads fail until capacity is freed or the operational limit is changed. Admission failures use stable 413 codes and English/Arabic messages in knowledge, file and Company Builder UI paths. Migration `0024_warm_loki.sql` was generated with `pnpm db:generate`, then extended with backfill/trigger SQL. The migration transaction blocks workspace/file writes during backfill and trigger installation. No settings UI is added.

This is **PARTIAL M5 remediation**. It bounds retained raw file bytes, including legacy data with understated size metadata. It does not bound row overhead/file count, knowledge chunk storage, indexing queue depth, global parser CPU/heap, all database storage, stale data retention, or disk headroom. Existing per-request extraction/body caps remain separate. The installation counter row still serializes admissions, but accounting work per admission is independent of retained-file row count. No scale measurement or complete M5 acceptance is claimed. Flow deletion does not delete retained files (there is no flow-to-file ownership FK), and no retained-file cleanup job exists.
